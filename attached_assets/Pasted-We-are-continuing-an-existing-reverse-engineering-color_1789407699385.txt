Before refactoring any Leica code:

1. Extract a WORKING COPY into the project.
2. Inventory every file.
3. Identify scripts, payloads, manifests, LUTs, fixtures, captured tables, documentation, hashes, IDs, and generated artifacts.

5. Preserve known-good payloads as fixtures.
6. Only then wrap/refactor the existing implementation into application modules.

The Leica custom-Look transport problem has already been solved.

Known established behavior includes:

- Leica Q3/Q3 43 family
- Leica FOTOS establishes the authorized relationship
- independent PTP/IP client inherits/reuses the surviving authorized session
- camera endpoint historically used: 192.168.54.1:15740
- DeviceInfo opcode 0x1001 works
- Leica Look-table read opcode 0x9033 works
- Leica Look upload/write opcode 0x9035 works
- response 0x2001 means success
- surviving session behavior may return 0x201E and must not automatically be treated as fatal
- session 0x412 was observed in working traces
- arbitrary custom IDs are used instead of Leica-reserved Look IDs
- the authoritative implementation contained in v1.2 overrides all earlier experiments, reconstructed packs, assumptions, and older payloads

Do not recreate Leica Looks from memory.

PRODUCT NAME:

Infinite Arch Photo Lab

CORE IDEA:

One photographic Look should have multiple camera implementations.

Example:

IA Presence
    Leica Q3/Q3 43 implementation
    Fuji X-E5 implementation
    Fuji GFX50R implementation
    Software/LUT implementation
    Lightroom/DCP implementation

The Infinite Arch Look is the master concept.

Individual camera recipes/payloads are target-specific implementations.

ARCHITECTURE:

Use a monorepo containing:

- React + TypeScript frontend
- Python FastAPI backend
- shared Python color-processing engine
- Leica compiler/parser modules
- Fuji recipe engine
- PostgreSQL
- persistent asset abstraction
- separate local Camera Bridge

The cloud application must NOT attempt to directly access a camera at a private LAN address such as 192.168.54.1.

Camera communication is handled by a local companion process called:

IA Camera Bridge

The bridge runs on the user's Mac initially.

It establishes an outbound authenticated connection to the Replit service.

The browser communicates with Replit.

Replit sends jobs to the bridge.

The bridge communicates with Leica/Fuji hardware.

THE BRIDGE SHOULD BE SMALL.

Do not duplicate Photo Lab's Look/color logic inside the bridge.

PHASE B:

Native Fuji camera-side RAW processing.

Long-term objective:

RAF
→ selected Infinite Arch Look
→ target-specific Fuji recipe/parameters
→ connected Fuji camera processes RAF using its native engine
→ processed output returned to Photo Lab

This should investigate/reproduce the useful X RAW Studio camera-processing workflow.

Do not claim generic cloud RAW conversion is equivalent to native Fuji rendering.

SECURITY:

Never expose Leica/Fuji camera transport services directly to the public Internet.

The local bridge creates outbound connections to Replit.

Use short-lived bridge pairing tokens.

Validate every payload checksum before camera upload.

Do not store credentials in source files.

Use Replit Secrets/environment variables.

TESTING RULE:

Before changing working Leica code, create a regression test demonstrating current behavior.

If a refactor changes known-good output unexpectedly, stop and investigate.

Do not "fix" differences by rewriting fixtures.

The fixtures define the expected behavior.
